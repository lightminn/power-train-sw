# 자동 그리퍼 교체 개발 계획

> 작성 2026-10-16. 초기 작성은 구현 착수 전이었다. 현재 §5-1~4 구현·mock 검증을 마쳤고,
> §5-5 실기 인수와 §5-6 최종 마감은 남아 있다.
> 선행 작업: `docs/specs/2026-10-14-arm-toolchanger-lock.md`(모터1 잠금 설계),
> `docs/reports/2026-10-15-arm-toolchanger-sequence.md`(잠금 시퀀스·GUI 결과).
> 이 문서의 모든 "확인됨" 항목은 아래 §9의 근거 파일·행 번호로 검증 가능하다.
> **2026-10-16 사용자 결정 4건을 §8에 반영했다.** 설계가 그 결정을 따른다.

## 1. 목표

차체에 미리 둔 그리퍼 도크 위치를 기억해서, 팔이 스스로 이동해 현재 도구를 지정한
도크에 해제하고, 다른 도크로 이동해 모터1을 돌려 새 도구를 결합한 뒤 원 자세로 복귀한다.

운용 단위는 **한 번의 교체 미션**이며, 사람이 시작을 명시적으로 지시한다.
완전 무인 자동화는 이번 범위가 아니다.

### 범위 밖 (명시)

- 비전으로 도크를 찾는 경로. §4-1 결정에 따라 쓰지 않는다.
- 미션 FSM(구간2 픽앤플레이스) 자체의 변경.
- 잠금 기구의 볼 캠 연동 모델링, 실기 하중·내구 시험.
- 파워트레인 계약 토픽 어휘 변경(양 팀 합의 사항이다).

## 2. ⚠️ 선결 차단 요인 — 지금 구조로는 자동 교체가 불가능하다

**이 세 조건이 서로 모순이라 다른 작업을 먼저 하면 전부 헛일이 된다. 1단계가 여기다.**

| # | 조건 | 근거 |
|---|---|---|
| ① | 잠금 `CHANGE`/`LOCK`/`UNLOCK`은 **MANUAL + END_EFFECTOR_ONLY**에서만 받는다 | `moveit_dynamixel_bridge.py` `_toolchanger_command` |
| ② | 팔 궤적은 **END_EFFECTOR_ONLY면 거부**된다 | 같은 파일 `trajectory_callback` 선두 |
| ③ | 팔 궤적은 `tool_motion_allowed`를 요구하고, 도구가 버스에서 미발견이면 이 값이 False가 된다 | 같은 파일 기동 분기 `elif self.tool_ids and not self.tool_discovered` |

즉 **팔을 움직이는 범위에서는 잠금을 돌릴 수 없고, 잠금을 돌리는 범위에서는 팔이 움직이지
않으며, 도구를 떼고 나면 둘 다 막힌다.**

### 해소 방침 (느슨하게 풀지 않는다)

기존 게이트를 완화하거나 "자동 모드면 건너뛰기" 분기를 넣는 방식은 **금지**다
(저장소 원칙: 안전 게이트에 스킵 분기를 넣으면 실기에서 켜진 채 돈다).

대신 **교체 전용의 좁은 제3 경로**를 만든다.

- 새 제어 범위 `TOOL_CHANGE`를 추가한다. 이 범위에서만 팔 궤적과 잠금 명령이 **둘 다** 허용된다.
- 진입은 운용자의 명시적 arm(무장) 1회로만 가능하고, 그 세션에서는
  **미션 픽앤플레이스 명령을 받지 않는다**(교체와 작업은 상호 배타).
- 진입 전제: 비상정지 비활성, **`/chassis_mode == MISSION_STOP`이 신선함**
  (2026-10-16 결정 — 계약 어휘를 새로 만들지 않고 기존 작업 허가를 재사용한다),
  도크 포즈 표 검증 통과.
- 이탈(완료·실패·비상정지)은 자동이며, 이탈 시 팔 토크 유지·도구 토크OFF로 둔다.
- ③은 "도구 없음"을 **정상 상태로 인정**한다. 도구 미발견을 곧 팔 정지로 번역하는
  현재 규칙을 **전역에서 제거**한다(2026-10-16 사용자 결정).
  - ⚠️ **수용한 위험**: 이 규칙은 교체 구간만 잡는 게 아니라 **일반 픽 미션 중
    그리퍼가 버스에서 떨어진 경우**(케이블 빠짐·통신 실패)도 잡고 있었다. 전역에서
    풀면 그 상황에서도 팔이 계속 움직인다. 사용자가 이 대가를 알고 선택했다.
  - 도구 **동작** 게이트는 그대로 둔다. 미발견 도구에 토크를 걸거나 개폐 명령을 보내는
    경로는 계속 막힌다. 완화 대상은 **팔 궤적 허용 조건 하나**로 한정한다.

## 3. 확인된 사실 — 움직인 것과 안 움직인 것

계획을 세울 때 이 구분을 지킨다. 안 움직인 경로 위에 기능을 얹지 않는다.

### 실기에서 움직였다

- **analytic IK 픽 경로**: 병 인식 → analytic IK → 하강 → 그리퍼 닫힘 →
  전류 기반 파지 판정까지 실모터 end-to-end 확인. `ik_mode` 기본값이 `analytic`이다.
- 단, 이 IK는 **위치 3개만** 맞추고 방향을 버리며 5축에서 2자유도가 남는다.
  같은 목표에서도 손목 각도가 매번 달라지는 문제가 실기에서 관측됐다.

### 실기에서 움직인 적 없다

- **MoveIt 경로**(`ik_mode:='moveit'`). 볼 잠금 URDF 기준 2026-10-14 검사 결과:
  - joint4 **±0.02 rad(1.15°)** PTP 1건만 계획·실행 성공, 가상 모터 환경.
  - 5축 동시 ±0.02 rad 후보 2개는 중간 자세 충돌로 전부 탈락.
  - **OMPL은 매 시행 시간초과(code −6)**, 기본 어댑터 복원 후에도 동일.
  - 자기충돌 **10쌍을 임시 제외**해야 통과했고 그 제외는 저장소 SRDF에 없다.
  - PTP용 가속도 1 rad/s²는 실측값이 아니며 저장소에 반영되지 않았다.

**결론: 자유 계획(OMPL)과 MoveIt pose goal에 의존하는 설계는 지금 쓸 수 없다.**

### 과거 "안 움직였다"의 실제 원인

- **계약 게이트**: `arm_fsm`은 `/chassis_mode == MISSION_STOP` **AND** 같은 mission_id의
  `/arrival_status`를 둘 다 신선하게 받아야 전이한다. 벤치엔 파워트레인이 없어 영구 락이다.
  `ros2 topic pub`는 `header.stamp`가 0으로 고정돼 첫 샘플만 통과하고
  `chassis_mode_timeout` 1초 뒤 락이 걸린다. 증상은 "명령은 가는데 팔이 안 움직인다"다.
  → 해법은 이미 있다: 벤치 전용 `mission_console` 노드(그 두 토픽을 10Hz 단조증가
  stamp로 직접 발행하고, 다른 발행자가 있으면 기동을 거부한다). **production 금지.**
- **버스 중복 소유**: 이전 픽 스택이 살아 있으면 브리지 둘이 같은 `/dev/ttyUSB0`을 두드려
  `COMM_RX_TIMEOUT`으로 **그리퍼 초기화만 조용히 실패**한다. 증상은
  "팔은 가는데 그리퍼가 안 닫힌다". `scripts/run_pick.sh`가 사전 정리를 한다.

## 4. 설계 결정

### 4-1. 도크 위치는 관절각 teach & replay로 외운다 (비전 미사용)

차체 도크는 **고정·반복 위치**다. 관절각을 직접 기억하면 비전·IK·OMPL을 전부 우회하므로
§3의 OMPL 시간초과, analytic IK의 남는 2자유도, 방향 무시 문제가 한 번에 사라진다.

비전은 박스가 임의 위치일 때 필요한 수단이고, 도크에는 실패 모드만 늘린다.

### 4-2. 다점 궤적을 쓰지 않는다 — 단계마다 별도 궤적

브리지의 궤적 처리부는 **`msg.points[-1]`만 읽고 중간 점을 모두 버린다.**
액션(`/arm_controller/follow_joint_trajectory`)과 토픽
(`/arm_controller/joint_trajectory`) 둘 다 같은 콜백으로 들어가므로 **액션도 마찬가지다.**

→ 접근·안착·후퇴를 한 궤적에 담으면 팔이 중간을 건너뛰고 직선으로 간다.
**단계마다 단일 목표 궤적을 따로 발행하고, 도착을 확인한 뒤 다음 단계로 간다.**
(기존 `_run_stow_sequence`가 같은 이유로 이미 이 방식을 쓴다.)

### 4-3. 액션 결과를 "도착"으로 믿지 않는다

`execute_follow_joint_trajectory`는 궤적을 모터에 보낸 직후 **즉시 SUCCESSFUL을 반환**한다.
도착 여부를 보지 않는다.

→ 각 단계 완료 판정은 **`/joint_states` 관절각이 목표 허용오차 안에 들어오고 정지**한
것으로만 한다. 시간 대기나 액션 결과를 완료 근거로 쓰지 않는다.

### 4-4. 안착 판정은 관절각 하나로만 한다 (2026-10-16 사용자 결정)

도크 위치는 **항상 고정**이므로 관절각을 저장·불러오는 것으로 충분하다고 결정했다.

- 각 단계 완료 판정은 **목표 관절각 도달 + 정지**뿐이다.
- **결합/해제 센서 확인을 넣지 않는다.** 리미트 스위치도 달지 않는다.
- 결합 부하 프록시도 이 시퀀스의 판정에 쓰지 않는다. 기존 수동 경로의 기능으로만 남긴다
  (기본값 0 = OFF 유지).
- ⚠️ **수용한 위험**: 도크가 도구를 실제로 받치고 있는지 아는 수단이 없다. 덜 들어간
  상태에서 해제하면 **그리퍼가 떨어진다.** 사용자가 떨굼을 수용 가능한 위험으로 판단했다.
- 그래서 **공짜로 얻는 보호는 그대로 유지한다**: 목표 관절각에 도달하지 못했거나
  이동이 제한시간을 넘기면 UNLOCK/LOCK을 발행하지 않고 ABORTED로 끝낸다.

### 4-5. 주기 감시는 이번에도 넣지 않는다

2026-10-15 사용자 결정을 유지한다. 따라서 **잠금 이동 순간에만 결합을 추정하고,
정지 상태에서 도구가 빠지는 것은 감지하지 못한다.** 자동 시퀀스에서는 이 한계가
수동 벤치보다 크므로, 교체 직후 1회 확인 단계(§5-4)로 부분 보완한다.

---

### 4-6. 교체 전용 입력 (2026-10-16 추가 사용자 결정)

교체용 입력 `/toolchanger/arm_trajectory`를 따로 둔다. `TOOL_CHANGE`에서는
기존 `/arm_controller/joint_trajectory`와 FollowJointTrajectory 액션, 수동·진단 팔 입력을
거부한다. 두 입력은 안전 권한을 별도로 검사하고 같은 모터 쓰기 함수를 공유한다.
토픽 분리는 발행자 인증을 의미하지 않는다. 교체 세션의 무장·차체 정지·비상정지 검사는
전용 입력에도 적용한다. 기존 FULL_ROBOT/END_EFFECTOR_ONLY 입력은 유지한다.

---

### 4-7. 도구 이름으로 고정 자리 선택 (2026-10-16 추가 사용자 결정)

운영자는 원하는 도구 종류만 지시한다. 현재 장착 도구의 고정 자리는 비어 있다고 보고
그 자리에 내려놓은 뒤, 요청 도구의 고정 자리에서 결합한다. 명령에 두 슬롯을 지정하지
않는다. 표에는 도구 종류당 고정 자리 하나만 허용한다. 현재 장착 도구가 불명확하거나
자리가 미보정이면 추측하지 않고 거부한다. 슬롯 점유·결합 센서는 추가하지 않는다.

## 5. 구현 단계

각 단계는 **검증 기준을 통과해야** 다음으로 간다. 단계별로 커밋한다.

### 5-1. `TOOL_CHANGE` 범위 신설 (§2 해소)

팔 궤적과 잠금 명령이 공존하는 좁은 경로를 만든다. 진입 전제는
비상정지 비활성 + 신선한 `MISSION_STOP` + 운용자 무장 1회다(§8-2).

도구 미발견 완화는 **별건으로 전역 적용**한다(§8-4) — 팔 궤적 허용 조건에서만
그 조건을 제거하고, 도구에 토크를 걸거나 개폐를 보내는 게이트는 건드리지 않는다.

→ verify: 기존 `END_EFFECTOR_ONLY`/`FULL_ROBOT` 동작 무변경(회귀 스위트),
`TOOL_CHANGE`에서 팔 궤적·잠금 명령 양쪽 수락, 그 밖 범위에서 여전히 거부.
**음성 대조 3건**: ① 무장 없이 `TOOL_CHANGE` 진입 → 거부, ② `MISSION_STOP`이
없거나 노후화된 상태에서 진입 → 거부, ③ 도구 미발견에서 도구 토크·개폐 명령 →
여전히 거부(완화가 팔 궤적에만 적용됐음을 증명).

### 5-2. 도크 포즈 표 (teach & replay)

토크를 풀고 손으로 팔을 도크에 맞춘 뒤 관절각을 캡처해 JSON에 저장한다.
기존 잠금 영점 캡처(`capture_zero`/`save_zero`)의 atomic 저장·검증 패턴을 그대로 따른다.

- **슬롯 3개**로 시작한다(2026-10-16 사용자 결정). 표 기반이므로 개수는 데이터로 늘린다.
- 슬롯별로 **접근 포즈 / 안착 포즈 / 후퇴 포즈** 3점을 기억한다.
- 저장 항목: 슬롯 id, 관절 이름·각도, 허용오차, 캡처 시각, 도구 종류.
- 로드 시 관절 이름이 현재 `JOINT_CONFIG`와 일치하고 리밋 안인지 검증한다.
  불일치면 미보정으로 시작하고 자동 교체를 막는다.

→ verify: 저장/로드 왕복, 관절 이름·리밋 위반 거부, 파일 손상 시 미보정 처리.
토크OFF·정지 상태에서만 캡처 허용(음성 대조 포함).

### 5-3. 교체 시퀀스 코어 (순수 파이썬)

`toolchanger_sequence.py`와 같은 결로 ROS 비의존 코어를 만든다. 상태:

```
IDLE → ARMED → TO_RELEASE_APPROACH → TO_RELEASE_SEAT → SEAT_CHECK
     → UNLOCK → RETREAT → TO_PICKUP_APPROACH → TO_PICKUP_SEAT → SEAT_CHECK
     → LOCK → RETREAT → TO_HOME → DONE
실패는 모두 ABORTED (fail-closed)
```

`SEAT_CHECK`는 **관절각 도달·정지 확인만** 한다(§4-4). 센서·부하 판정은 없다.

- 팔 이동 1단계 = 단일 목표 궤적 1회 발행 + 관절각 도착 확인(§4-2, §4-3).
- 각 단계에 **이동 제한시간**과 **관절각 허용오차**를 둔다.
- `UNLOCK`/`LOCK`은 기존 `ToolchangerSequence.start()`를 그대로 호출한다. 재구현 금지.
- 중단 시: 진행 중 궤적 취소 + 현재 자세 홀드, 잠금 토크OFF, confirm 미발행.
- 비상정지·차체 모드 변경·피드백 노후화는 즉시 ABORTED.

→ verify: 단계별 중단 경로 단위테스트. 각 실패에서 **잠금 confirm 미발행**과
**다음 단계 궤적 미발행**을 단언한다.

### 5-4. ROS 어댑터 + 교체 직후 확인

- 명령: `/toolchanger/change_tool` (슬롯 id, 대상 도구). 상태: `/toolchanger/change_status`.
- 교체 직후 1회 확인: 결합 프록시 결과 + 새 도구가 버스에서 발견되는지 + 기존
  `/tool/change` 재준비가 READY로 끝나는지. 하나라도 실패면 ABORTED로 두고 도구를 켜지 않는다.

→ verify: 설치된 `ros2 run` 엔트리포인트로 mock E2E. 정상 1회 + 단계별 실패 주입.
**음성 대조**: 안착 미달에서 UNLOCK이 발행되지 않는 것을 확인.

### 5-5. 벤치 실기 (사람 입회, 바퀴/차체 정지)

도구를 물리지 않은 상태에서 포즈 이동만 먼저 → 더미 도구로 결합/해제 → 실제 그리퍼.

→ verify: 단계별 육안 확인 + `/joint_states` 기록. 떨굼 0회를 인수 조건으로 둔다.

### 5-6. 마감 — 결과 기록과 임시 포인터 제거

- `docs/reports/`에 결과를 남긴다(실측한 도크 관절각, 통과한 검증, 수용한 위험의 실제 결과).

## 6. 먼저 실측해야 하는 값

**이 값들이 없으면 자동 시퀀스는 판정을 못 한다. 추정값으로 기본값을 박지 않는다.**

- **도크 슬롯 3개 × 접근·안착·후퇴 관절각과 허용오차.** 이번 설계에서 실측이
  필요한 값은 사실상 이것 하나다(§4-4 결정으로 센서·부하 판정을 뺐다).
- 단계별 이동 제한시간. 실제 이동 시간을 재서 여유를 두고 잡는다.
- 결합 부하 임계값은 **이번 시퀀스의 선결 조건이 아니다**. 수동 경로 기능으로만 남으며
  기본값 0(OFF)을 유지한다.
- **교체 대상 도구의 파지/낙하 임계값.** 도구마다 따로 측정돼야 한다.
  `config/tool_profiles.yaml` 현재 상태: `dual_motor_gripper`는 실측 완료
  (no_load 119 / grasp 290 / grasp_threshold 250 / release_drop_threshold 200),
  **`spur_1motor_gripper`는 `grasp_effort`·`grasp_threshold`·`release_drop_threshold`가
  모두 `null`로 미측정**이다(파일 주석에 "effort/grasp calibration remains pending" 명시).
  이 도구로 교체하면 교체 후 파지 판정을 할 수 없다.
  (참고: `gripper_presets.py`의 과거 placeholder 80/20은 2026-08-07 실측으로
  140/120으로 교체됐고 "80/20은 실제로 틀렸다"고 주석에 남아 있다. 혼동하지 말 것.)
- PTP 가속도·속도 scaling. 현재 가상 환경에서만 쓴 값이다.
