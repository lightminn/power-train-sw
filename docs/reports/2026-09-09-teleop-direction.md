# 2026-09-09 원격주행 방향·조향 장착 부호 교정

RT가 후진하고 LT가 전진한다는 운전자 관찰과 단일축 조향 시험을 근거로
입력 및 모터 경계의 부호를 교정했다. **실차에서 보고된 X자 현상 전체가 해결됐다는
판정은 아직 하지 않는다.** 수정 후 실제 주행 방향·조향·영점 확인은 운전자 인수 대상이다.
이번 범위는 원격주행이며 자율주행, 의도적으로 분리한 US-100·L515는 제외한다.

## 실제로 확인한 것

DualSense SDL 매핑은 LT=axis2, RT=axis5, 왼쪽 스틱=axis0으로 현재 입력 어댑터와
일치했다. 실제 패드를 로컬에서 읽어 기존 encode/decode/gateway/kinematics를 통과시켰을 때
RT=1/LT=0은 v=+1.5였다. 이 관측은 로봇에 명령을 보내지 않은 재생이며 당시 실차 CAN
추적 기록을 대신하지 않는다. 사용자는 기존 런타임에서 이 RT 입력이 후진함을 두 번 보고했다.

모터 제어 프로세스를 정지한 뒤 사용자 승인을 받아 AK 한 축씩 raw +30° → 기존 위치
복귀 → zero RPM을 실행했다. 각 단계는 오차 0.6° 이내 도달 후 3초 유지했다.
처음 CAN1은 +5°로 시험했으나 육안 식별이 어려워 사용자가 30°로 확대를 요청했다.

| CAN ID | 사용자가 식별한 바퀴 | raw +30°의 실물 방향 | 복귀 판정각 / 정지 후 각도 |
|---|---|---|---|
| 1 | 앞왼쪽 | 시계방향, 바퀴 앞끝은 차체 오른쪽 | −1.9° / +2.1° (시작 −2.4°) |
| 2 | 앞오른쪽 | 1번과 동일 | +0.5° / +2.2° (시작 0°) |
| 3 | 뒤왼쪽 | 동일한 시계방향 | +1.0° / +5.1° (시작 +0.5°) |
| 4 | 뒤오른쪽 | 동일 | +0.4° / +0.4° (시작 0°) |

따라서 CAN1/2/3/4의 위치 매핑은 맞으며 **네 축 모두 raw +가 차체 기준 +조향(좌회전)과
반대**다. 뒤쪽 모터가 뒤를 바라본다는 외형만으로 뒤축 부호를 따로 바꾸는 가설은 배제했다.
복귀 제어 종료 후 일부 각도가 달라졌으므로 영점 일치·부하 해제 후 위치 유지까지 통과로
판정하지 않는다. 영점 저장·NVM·ODrive 펌웨어·CAN link 설정은 이 조사에서 변경하지 않았다.

각 시험에서 구동 11–16은 모두 IDLE/error 0, 조향 1–4는 fault 0이었다. 마지막 별도
수신 점검에서도 같았고 CAN TX packet 수는 331125 → 331125로 변하지 않았다.

## 수정 원리

- **패드 좌우:** SDL 스틱 오른쪽은 +left_x이지만 차체 +yaw는 좌회전이다.
  `RemoteInputGateway`를 `−left_x × max_angular`로 고쳤다. 기존 직접 텔레옵 경로와
  같은 규약이며 잘못된 원격 식은 2026-07-14 커밋 `1b4932e3`부터 존재했다.
- **구동 전후진:** 실기 CAN/USB 빌더는 좌측 바퀴만 invert한다. 전진 raw 모터 속도는
  좌(11/13/15)−, 우(12/14/16)+다. 오른쪽=보드 axis1이라는 배선 검증은 유지하고
  전기적 부호와 분리했다. 노드 번호를 부호 판정에 하드코딩하지 않고 wheel_map의
  바퀴 이름에서 유도한다. 개별 구동축의 물리 위치는 이번에 재식별하지 않았다.
- **조향:** 실기 빌더에서 `SteerAk40(invert=True)`를 사용한다. 목표각과 실제 피드백을
  모두 반전하며 arm에서는 현재 raw 각을 차체 각으로 바꿔 첫 tick의 위치 점프를 막는다.
  chassis·kinematics·odometry·텔레메트리는 계속 차체/바퀴 좌표계를 사용한다.
- CAN 주행 브링업과 USB 벤치 텔레옵의 전진 시퀀스도 같은 부호로 맞췄다. USB의
  `--raw-direction`은 양축 raw +를 사용하며 기존 `--no-invert-axis1` 별칭을 유지한다.
  `ak_control.py`와 `motor_gui`의 직접 raw 명령은 그대로 모터 좌표계다.
- 설치된 ROS 엔트리포인트 종료 시험에서 `rclpy.shutdown()` 중복 호출을 재현했다.
  SIGINT가 이미 종료한 context에는 shutdown을 다시 호출하지 않도록 수정했다.
  전체 루프 종료에서 같은 오류가 확인된 ops_broker에도 동일한 수정을 적용했다.

## X자 현상의 판정 한계

기존 `solve(v=0, ω≠0)`은 제자리선회 경로다. ω의 좌우 부호가 바뀌어도 바퀴 방향은
동일한 X 배치(±45° 제한)이고 구동 방향만 뒤집힌다. 현 기하에서 무슬립 제자리선회에
필요한 앞 약 58.1°·뒤 약 64.1°는 조향 한계 45°를 넘는다. 이 경로의 마찰·끄는 현상은
부호 교정만으로 제거되지 않는다.

실제 패드 기록에서는 RT를 누른 상태의 좌/우 입력이 서로 다른 정상 4WS 목표각을 만들었다.
그러나 당시 실차의 최종 v/ω·CAN 지령을 기록하지 못했으므로 사용자가 주행 중 관찰한 X자를
제자리선회로 단정하지 않는다. 수정 후에는 입력 Twist·실제 CAN 목표·조향 피드백을 함께
기록해 남은 문제를 확인해야 한다. 별도 pivot 모드나 kinematics 변경은 이번에 추가하지 않았다.

노트북 첫 전체 실행의 1건 실패는 열어 둔 콘솔의 패드 단일 소유권과 충돌한 것이었다.
콘솔과 자식 종료 후 전체 1085개를 다시 통과했다. Jetson 모터 테스트는 ROS overlay를
제외한 순수 Python 환경에서 실행했다. overlay를 함께 적용했을 때 기존 DEBUG 로그
캡처 테스트 1건이 실패했으며, 모터 수신 동작은 정상이고 별도 실행에서 로그 발생도 확인했다.
ROS 엔트리포인트는 별도 overlay 환경으로 검증했다. 가상 CAN 검증은 실제 모터 검증과 구분한다.

가상 CAN 전체 루프는 `--network none` 컨테이너 안의 vcan77만 사용했다. can0·USB 장치를
노출하지 않았으며 런타임 lock 디렉터리도 컨테이너 전용 tmpfs였다. 입력 클라이언트와 UDP
수신도 같은 격리 환경에서 실행했으므로 이번 결과는 무선 링크 인수를 포함하지 않는다.
시험 도구에서 발견된 ROS discovery 대기 부족, 상태 파일 동시 읽기, launch와 자식에 대한
중복 SIGINT 전달을 수정한 뒤 전체 경로와 종료 로그까지 다시 통과했다.

실차 재시험에서는 통합 런타임을 복원하고 콘솔의 명시적 운전 시작을 사용한다. 구동 방향과
주행 중 조향을 육안으로 확인하며 입력·raw CAN 지령·피드백을 함께 수집한다. 부호 수정의
가상 검증 결과를 실차 인수 통과로 올려 쓰지 않는다.
