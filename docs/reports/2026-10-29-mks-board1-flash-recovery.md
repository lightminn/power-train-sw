# MKS node11/12 보드 flash 복구와 patch4 적용

2026-10-29 Jetson에서 **serial `335233643235`, node11/12, MKS v3.6-56V** 보드를 복구했다.
이 보드는 CAN 버스에도 USB에도 나타나지 않았다. ROM DFU에서 application 섹터 1의 비트가
읽을 때마다 바뀌는 것을 확인했고, application만 **CAN patch4**로 다시 기록했다. NVM(설정·
캘리브레이션)은 지우지 않았다. 기록 뒤 정상 부팅해 USB 읽기 전용 인수를 통과했고, CAN
버스에서 처음으로 **10모터가 모두** 보였다.

같은 날 Jetson `can0`이 버스를 듣기만 하고 보내지 못하는 **송신 장애**도 있었다. CAN 트랜시버
ADM3053의 VIO 배선 오류였고, 바로잡은 뒤 해결됐다(아래 "Jetson `can0` 송신 장애"). 같은 날
node15/16 보드도 patch4로 갱신했다(`2026-10-29-mks-node15-16-patch4.md`).

증거: `2026-10-29-mks-board1-flash-recovery-evidence/` (파일 설명은 그 폴더의 README, 대조는 `SHA256SUMS`).
앞선 보드 적용 기록은 `2026-10-21-mks-can-patch4.md`, `2026-09-10-mks-second-board.md`다.
**"세션 관찰"로 표시한 값**(CAN 프레임 수, 송신 시험, 커널 메시지, 3·10·20회 읽기)은 원출력을
저장하지 않아 증거 파일로 재검산할 수 없다.

## 증상

| 관측 | 내용 |
|---|---|
| CAN (Jetson `candump`, 듣기만, 세션 관찰) | AK 1–4, ODrive 13–16은 3초에 100–130프레임. **0x161·0x181(node11/12)은 0** |
| USB 정상 부팅 (세션 관찰) | 커널 `usb 1-2.1: new full-speed USB device`까지만 찍히고 장치 설명자를 못 읽은 채 사라짐 |
| USB ROM DFU (BOOT0) | `0483:df11`로 바로 열거됨 — 케이블·포트·USB 회로는 정상 |
| 같은 케이블·포트 | node13/14(`336A33523235`)·node15/16(`337733643235`)은 정상 열거 |

ROM DFU는 칩 고정 부트로더이고 일반 부팅은 flash의 펌웨어를 실행한다. 일반 부팅에서만
실패하므로 flash 내용 쪽을 먼저 조사했다.

## flash 진단 (쓰기 없음)

ROM DFU 읽기 전용 스크립트로 1 MiB를 반복해 읽었다.

| 시험 | 결과 |
|---|---|
| 전체 3회 (증거 세 벌) | 세 번 모두 SHA256이 달랐다. 쌍별 차이 1–2바이트, 위치는 `0x08006FF2`·`0x080078AB` 두 곳뿐 |
| 섹터 1을 10회 (세션 관찰) | 6바이트가 흔들림, 비트 1–2개 (예: `0x080078AB` = C9 ×5 / 89 ×3 / E9 ×2) |
| application 768 KiB를 30회 | **14바이트가 흔들림, 전부 섹터 1(`0x08004000`–`0x08007FFF`) 안**(주소 JSON). 주소별로 첫 읽기와 다른 대체값을 세면 비트 폭 1이 14건, 2가 3건(세션 관찰) |
| NVM 256 KiB | 3회 모두 같음, SHA256 `86b374e8a3416d6a949a90e1350a5beb11478f516f0781ca08f1ee31e37442e0` |

흔들린 주소 목록은 `335233643235-unstable-30reads.json`이다. 확인된 사실은 **섹터 1에 국한된
읽기 불안정**이다. 같은 읽기에서 다른 섹터와 NVM은 매번 같았다. 원인은 확정하지 못했다. 셀
전하가 판정 경계 근처에 있었다는 설명(불완전 기록, 보존 열화, 전기적 스트레스 등)은 가설이다.
부팅 중 이 영역을 잘못 읽으면 펌웨어가 멈출 수 있어 USB·CAN 무응답과 맞지만, 이 인과도
직접 확인하지는 않았다.

원본 이미지는 세 번 읽은 것을 모두 보관했다(`335233643235-original-read{1,2,3}-1m.bin.gz`).
셋 다 섹터 1의 흔들린 바이트가 섞여 있어 정상 부팅 가능한 원본 기준선이 아니다.

## 기록

`tools/mks_dfu.replace_application`은 지우기 전에 현재 flash 전체가 백업과 같아야 한다.
이 보드는 섹터 1이 흔들려 조건을 통과할 수 없다. 그래서 `flash_board1_patch4.py`는 같은
application 전용 갱신을 하면서 사전조건 하나만 바꿨다.

- NVM은 세 백업 모두와 완전히 같아야 한다(보존 대상).
- application은 read1과 비교해 **섹터 1 안에서만** 달라도 된다.
- 지우기는 `DfuTransport.erase`가 허용하는 섹터 0–9만, 쓰기는 application 경계 안만.
- 실패 시 자동 원복 쓰기와 앱 점프를 하지 않는다. 원본이 정상 기준선이 아니고, 약한 섹터에
  추가 쓰기를 하지 않기 위해서다. ROM DFU는 항상 남는다.
- 실패해도 NVM을 다시 읽어 대조 결과만 기록한다(Codex P3 반영).

처음 사전조건은 10회 읽기에서 찾은 6바이트 목록만 허용했다. `check` 단계가 목록 밖
`0x08006F50`에서 거부했고(쓰기 없음), 30회 읽기 결과에 맞춰 섹터 1 범위로 바꿨다.

| 단계 (새 컨테이너, `motor_session` 잠금, CAN 소유자 정지) | 결과 |
|---|---|
| `check` | `precondition_diff []`, 이미지 SHA256 일치, `ready` |
| `program` | 지우기 직전 섹터 1 두 바이트(`0x8006ff2`, `0x80078ab`)가 read1과 달랐고 허용 범위 안. 섹터 0–9 지움 → patch4 기록 → **30회 다시 읽어 흔들린 주소 0**, NVM 불변 → `program_verified` |
| 사후 읽기 (새 프로세스, 세션 관찰) | 1 MiB 20회: application 불일치 0바이트, NVM 불일치 0회 |

적용 BIN은 node13/14와 같은 patch4 빌드다. 251,868 bytes,
SHA256 `15462f7f64745b03d1347fccda8091cd34b795056fefee64f87e794dc8a4b3fc`
(`2026-10-21-mks-can-patch4-evidence/build-patch4/ODriveFirmware.bin.gz`).

### Codex 교차검증

기록 전 적대 검토에서 **GO, P1/P2 없음**이었다. 검토가 따로 확인한 것은 다음과 같다.

- 백업 NVM을 로컬 patch4 빌드 트리의 소스·ELF 구조와 CRC 규칙으로 오프라인 해석했다(해석 출력·
  파서는 이 증거에 없다). 활성 설정은 섹터 10,
  CRC 잔여 0이고 node 11/12, 500 kbps, pp 10/cpr 60, encoder bandwidth 30, 전류 제한 9 A,
  UV/OV 40/56 V, 양축 `pre_calibrated=true`, `startup_*`·step/dir 비활성이다. 원본 펌웨어
  버전 자체는 확인하지 못했다.
- 호출 경로에 NVM 섹터 10/11 지우기·쓰기, 옵션 바이트, mass erase, read unprotect가 없다.
- 이미지 끝 `0x0803D000`–`0x0803D7DB` 쓰기는 정렬돼 있어 패딩이 필요 없다.
- 30회 연속 읽기는 기록 직후 검증일 뿐 전원 재인가 뒤 보존을 보장하지 않는다.

## Jetson `can0` 송신 장애 — 원인과 해결

보드 복구 전후 모두 Jetson은 버스를 듣기만 하고 **보내지 못했다**(모두 세션 관찰).

| 시험 | 결과 |
|---|---|
| 차체 서비스가 송신 | 5초 안에 송신 오류 248 → BUS-OFF, 자동 재시작 반복 (한 부팅에 bus-off 수천 회) |
| 소유자 정지 + `can_setup.sh` 재설정 뒤 `cansend 7FF#` ×5 | 송신 완료 **0**, 송신 오류 카운터 0, 수신 오류 약 120 (ERROR-WARNING/PASSIVE) |
| AK 1–4 위치 명령(+45°) 200개 | 소켓 쓰기는 성공, 송신 완료 0, 위치 변화 없음 |
| 커널 | `mttcan … can_put_echo_skb: BUG! echo_skb 0..12 is occupied!` 뒤 error passive → bus off |
| `mttcan` 모듈 재적재 | 같음 |
| 컨트롤러 내부 루프백 | 송신 완료 3, 자기 프레임 수신. 시험 뒤 `loopback off`와 LOOPBACK 플래그 없음을 확인 |
| 보드 1을 DFU에 둔 상태 / 10모터 정상 상태 | 둘 다 같음 |

내부 루프백 경로에서는 송신이 끝났으므로 트랜시버 쪽 외부 경로를 먼저 의심했다. 드라이버가
정상인지, 커널 echo 슬롯 오류가 송신 미완료의 결과인지는 이 시험만으로 확정하지 않았다.
보드 1의 영향도 DFU 비교로 배제하지는 못했다(아래 해결 뒤 결과로 무관함이 사실상 드러났다).

**원인 (사용자 확인)**: ADM3053(MikroE CAN Isolator Click)의 **VIO(로직 전원) 선이 Jetson 3V3
핀이 아니라 5V 핀에 꽂혀 있었다.** 그 상태에서 VIO가 약 **2.2 V**로 측정됐다(로직 GND 기준,
사용자 측정). Jetson 40핀 5V는 이 보드의 부하를 걸면 처진다는 2026-06 기록과 맞는다. 데이터시트
VIO 하한과의 비교는 따로 확인하지 않았다. VIO가 처져 있었으므로 그동안 트랜시버 RX 출력도 그
이하였을 것으로 보이나 측정하지 않았다.

**해결 뒤 (세션 관찰)**: VIO 선을 3V3으로 옮기고 소유자 정지 → `can_setup.sh` 재설정을 하자
다음과 같았다.

| 항목 | 결과 |
|---|---|
| `can0` | **ERROR-ACTIVE, 송신·수신 오류 0** |
| 3초 듣기 | 10노드 모두 **150프레임**(50 Hz) |
| `cansend 7FF#` ×5 | 송신 완료 |
| AK 1–4 +45° (2.5 s 명령) | id2 +44.9°, id3 +45.0°, id4 +45.0°; **id1은 +25.9°까지만, 전류 0.85 A** — id1 조향 부하 확인 필요 |
| 차체 서비스 재기동 15초 뒤 | ERROR-ACTIVE, 오류 0, chassis healthy |

이 장애 동안 생긴 bus-off 폭주로 patch3였던 node15/16에 CAN 복구 래치(`axis.error = 0x4000`)가
걸려 뒤쪽 두 바퀴가 시동되지 않았다. 보드 전원 재인가로 풀었고, 같은 날 patch4로 갱신했다
(`2026-10-29-mks-node15-16-patch4.md`).

## 남은 일

- node11/12 포함 실트래픽 인수(patch4 계획 Task 10 Step 2–7).
- 이 보드는 섹터 1이 약해졌던 이력이 있다. 전원 재인가 몇 회와 운용 며칠 뒤 ROM DFU로
  application을 다시 읽어 patch4 이미지와 대조한다. 다시 흔들리면 예비로 돌리거나, 섹터 1을
  비우는 링커 배치로 펌웨어를 다시 빌드한다.
- AK id1 조향이 같은 명령에서 다른 축보다 느리고 전류가 높았다. 기계 부하를 확인한다.
