# MKS CAN patch4 적용 — node15/16 보드

2026-10-29 Jetson에서 **serial `337733643235`, node15/16, MKS v3.6-56V** 보드를 CAN patch3에서
**patch4**로 갱신했다. 이로써 구동 보드 세 장(node 11/12 · 13/14 · 15/16)이 모두 patch4다.
절차와 스크립트는 2026-10-21 node13/14 적용(`2026-10-21-mks-can-patch4.md`)과 같고, 스크립트는
serial과 node 상수만 바꿨다.

증거: `2026-10-29-mks-node15-16-patch4-evidence/` (README, `SHA256SUMS`).

## 계기

같은 날 Jetson `can0` 송신 장애(ADM3053 VIO 배선 오류, `2026-10-29-mks-board1-flash-recovery.md`)
동안 bus-off가 수천 번 반복됐다. patch3는 CAN 오류에 양축 복구 래치를 거는 알려진 결함이 있어,
배선을 고친 뒤에도 rear_left/rear_right 구동축에 `axis.error = 0x4000`이 남았다. 차체는
`healthy: false`·`MOTION_HOLD`였고 콘솔 「경고 초기화」로는 풀리지 않았다(세션 관찰). 보드 전원
재인가로 래치를 푼 뒤 patch4로 갱신했다.

## 절차

CAN 소유자(`powertrain_chassis`, `powertrain_canwatchdog`)를 정지하고, 공유 `motor_session` 잠금
안에서 일회성 컨테이너(`powertrain-sw:jetson`, privileged, host network, `/dev/bus/usb`·
`/run/powertrain` 공유)로 단계마다 새 프로세스를 띄웠다.

| 단계 | 결과 |
|---|---|
| backup | 양축 IDLE·오류 0, 설정 307개 저장 → ROM DFU 진입. 같은 프로세스가 새 DFU 장치를 못 봐 종료(10-21과 같은 함정), 쓰기 없음 |
| backup-from-dfu | 1 MiB 두 번 읽기 일치·저장, 앱 복귀. 그 뒤 같은 프로세스의 앱 재탐색이 멈춰 컨테이너를 정지했다(10-21과 같음, 쓰기 없음) |
| program | 설정 차이 0, 양축 IDLE·오류 0 확인 → ROM DFU 진입. 같은 프로세스가 DFU를 못 봐 종료, 쓰기 없음 |
| program-from-dfu | 현재 flash = 백업 확인 → application 섹터 0–9만 지우고 기록 → application·NVM 전체 읽기 대조 통과(`program_verified`) → 앱 점프 |
| verify | 아래 인수 통과(`accepted: true`) |

## 인수 (USB 읽기 전용)

| 항목 | 값 |
|---|---|
| firmware | 0.5.1 unreleased, `can.reliability_patch = 4` |
| 설정 | 적용 전 307개와 차이 0 |
| 양축 (즉시·3초 뒤) | IDLE, 오류 0, 복구 래치 없음, `control_deadline_count` 0/0 |
| CAN 카운터 (부팅 직후 → 3초 뒤) | recovery 0→0, LEC 0→0, bus-off 0, error-passive 0, tx_drop 0 |

10-21 node13/14 인수는 버스가 끊긴 상태였다. 이번에는 **버스가 연결된 상태**에서 LEC가 0으로
유지됐다.

차체 서비스를 다시 올린 뒤 `/wheel_states`(세션 관찰)는 여섯 바퀴 모두 구동·조향 피드백 정상,
구동축 오류 0, 조향 고장 0, `healthy: true`였다. `can0`은 ERROR-ACTIVE, 오류 0이었다. 차체 모드는
컴포넌트 토글이 재기동으로 초기화돼 US-100 응답 없음 ESTOP이었다(US-100 미연결, 운용자가
콘솔에서 끄는 대상).

결과 JSON의 시각은 Jetson 시계 기준이며, 이날 Jetson 시계는 재부팅 뒤 실제 시각과 맞지 않았다.
