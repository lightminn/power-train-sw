# 경로 소스와 에지 가드의 분리

작성 2026-08-03. 대상 `powertrain_autonomy/terrain/estimator.py`,
`powertrain_autonomy/controller/core.py`.

## 1. 무엇이 문제인가

하나의 depth 추정기가 두 가지 질문에 동시에 답한다.

- **길이 어디인가** — 강건성이 필요하다. 답이 몇 cm 틀려도 다음 프레임에 고쳐진다.
- **바퀴가 지면 밖으로 나가는가** — 정밀도가 필요하다. 한 번 틀리면 로버가 떨어진다.

지금은 두 번째 질문의 실패가 첫 번째 질문의 답까지 파괴한다. `_summarize` 는
바퀴 지지가 확인되지 않으면 `_reject("unsupported_footprint")` 로 빠져나가고,
`_reject` 는 다음을 지운다.

```python
self._filtered_path_estimate = None
self._path_estimate_stamp_s = None
```

즉 **안전 판단 실패 한 번이 누적된 경로 기준선을 삭제한다.** 커밋 `0f9cd7a`(행 walk
연속성), `4252dc5`(인증 기준선 운반), `b626bac`(나쁜 depth 프레임 하나를 견딤)은
전부 이 삭제와 싸운 것이다. 원인을 두고 증상을 세 번 막았다.

## 2. 측정 근거

실코스 정지 지점의 저장 격자 12프레임(`runs/stopgrid`)을 오프라인 재생해 얻은 값이다.

| 관측 | 값 |
|---|---|
| 바퀴 밴드 셀 중 support | 55.7% |
| 미관측(depth 없음) | 41.6% |
| 분류기가 깎아낸 것(미연결+장애물+낙차) | 2.7% |
| 정지 지점 support run 폭 / 중심 | 0.800 m / +0.000 m |
| run 양 끝 바깥의 정체 | 12프레임 전 행에서 **낙차 아님, 미관측** |

로버는 여섯 바퀴가 물리적으로 다 놓이는 지면 위에 서서 기각당했다. 기각의 원인은
지형도 분류기도 아니고, 게이트가 요구한 여유였다(별건으로 수정).

`left_wheel_clearance_m` / `right_wheel_clearance_m` 는 계산·발행되지만 컨트롤러가
읽지 않는다(`controller/core.py` 는 `path_available` 만 본다). 연속 에지 신호를
만들어두고 쓰지 않은 채, 이진 게이트 하나에 안전 전체를 걸고 있었다.

## 3. 설계

### 3.1 추정기 — 경로는 안전 판단과 무관하게 발행한다

`unsupported_footprint` 는 더 이상 `_reject` 를 호출하지 않는다. 중심선이 적합되면
추정치를 정상 발행하고, 확인 실패는 `degradation_reasons` 에 남긴다.

`TerrainEstimate` 에 필드 하나를 추가한다.

```
confirmed_support_m: float
    여섯 바퀴 지지가 모두 확인된 가장 먼 전방 거리(m).
    확인된 행이 하나도 없으면 0.0.
```

값은 이미 계산 중인 `wheel_supported_row_indices` 에서 나온다 — 그 집합의 최대
행 인덱스에 해당하는 `x_centres` 값이다. 새 계산이 아니라, 버리던 정보를 내보내는
것이다.

`no_connected_support` 와 `centreline_unresolved` 는 그대로 `_reject` 를 유지한다.
그것들은 "길이 어디인지 답할 수 없다"이지 "안전하지 않다"가 아니다.

### 3.2 컨트롤러 — 확인된 거리 밖으로 나가지 않는다

```
confirmed_support_m > 0.0   → 전진 허용
confirmed_support_m == 0.0  → 전진 정지(hold), 단 경로 추정은 살아 있다
```

hold 사유는 `unconfirmed_support` 로 기록한다. 기존 `path_unavailable` 과 구분해야
"길을 모른다"와 "길은 아는데 바퀴 자리가 확인이 안 됐다"를 텔레메트리에서 나눌 수 있다.

정지거리 모델이나 비례 감속은 넣지 않는다. 규칙 하나로 끝낸다.

### 3.3 이 설계가 지키는 것

이진 게이트보다 약하지 않다. 지금은 게이트가 통과하기만 하면 전방 어디까지 확인됐는지와
무관하게 프로파일 최대 속도를 낸다. 바뀐 뒤에는 확인된 지지가 없으면 전진하지 않는다는
성질이 명시적으로 남는다.

바뀌는 것은 **실패의 대가**다. 확인 실패가 경로 기준선을 파괴하지 않으므로, 로버는
확인이 돌아오는 즉시 이전 기준선으로 주행을 재개한다. 지금은 매번 처음부터 다시
쌓는다.

## 4. 검증

- 호스트 `powertrain_autonomy/tests/` 전수. 새 필드의 계약 테스트와, 확인 실패
  프레임에서 `path_available` 이 유지되고 `_filtered_path_estimate` 가 살아남는
  테스트를 추가한다.
- Isaac 8패밀리 캠페인 seeds 0,1,2 — **`fail_open` 과 `edge_overrun` 이 기준선 대비
  악화되지 않아야 한다.** 하드 게이트를 소프트로 바꾸는 변경이므로 이 항목이 수용 조건이다.
- Isaac 실코스 60 s / 300 s. 거리와 `TRACKING` 틱뿐 아니라 **렌더 프레임으로 실제 코스를
  달리는지 확인한 뒤에** 수치를 읽는다(경사로를 코스로 오독한 전례).
