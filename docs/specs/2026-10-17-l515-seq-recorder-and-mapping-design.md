## 1. 기록 도구 L0 — `lidar_dev/record_seq.py`, `lidar_dev/check_seq.py`

### 1.1 목적
1. 깊이 잡음 보정용 정지 기록(벽 거리별)
2. 지도·장애물 개발용 이동 기록(실측 치수가 있는 장면)
3. 시뮬과 같은 장면 비교 기록

### 1.2 호환 범위
- **v1 호환 보장 범위는 640×480 원시 깊이다.** 인수받은 `terrain.load_detector()`는 meta의 크기를 쓰지 않고 (480, 640)을 가정한다. `overlay.py`·`scan_terrain.py`도 같다. `ground.py`·`view_depth.py`는 실제 크기를 쓴다
- `--depth-res 1024x768`은 "terrain 계열 비호환"으로 meta에 표시하고 실행할 때 경고한다
- `scan_terrain.py`는 작업 디렉터리 기준 `data/*/`만 찾는다. 돌릴 때는 기록 폴더의 부모 디렉터리에서 `data` 링크를 만들거나 그 부모에서 실행한다. 절차는 사용법에 적는다
- "오프라인 폴더 호환"(이 도구)과 "ROS 노드 호환"(`terrain_node.py`)은 별도 인수 항목이다

### 1.3 출력 형식
```
<out>/<YYYYmmdd_HHMMSS>[_<label>]/
  meta.json
  depth/000000.png        # uint16 z16 원본, 깊이 optical 좌표, 640×480 기본 — 호환 필수
  infrared/000000.png     # uint8 IR, 깊이와 같은 센서·같은 화소 격자(기본 켬)
  color/000000.jpg        # 컬러(1280×720 기본, JPEG 95)
  # (v1에는 정렬 깊이를 기록하지 않는다 — 컬러 정렬은 meta 외부 파라미터로 후처리하는 후속 기능)
  frames.csv              # 저장 확정된 프레임만, 저장 번호 순
  imu.csv                 # IMU 원래 주기 그대로(영상 저장 간격과 무관)
  capture_log.csv         # 수집 측이 받은 모든 frameset(버림 포함), 수집 순
```
- 같은 번호의 depth·infrared·color가 한 frameset이다. 같은 번호가 동시 노출을 뜻하지는 않는다. 스트림별 타임스탬프로 시간차를 따로 본다
- 파일은 임시 이름으로 쓴 뒤 rename한다. 쓰다 만 파일이 정상 파일처럼 남지 않게 하기 위해서다

`meta.json`:
- 형식: `format: "l515-seq"`, `format_version: 1`, `created_wall`(ISO), `label`, `note`, `tool_version`
- 장치: `device{name, serial, firmware, usb, product_line}`, `sdk_version`
- 스트림: `streams{depth, ir, color, accel, gyro}` — 요청값과 **실제 협상 결과**(w·h·fps·format)
- 저장 간격: `every`
- 호환 키: `depth_scale_m`, `depth_intrinsics{width, height, fx, fy, ppx, ppy, model, coeffs}`, `color_intrinsics`(컬러 없으면 null)
- 호환 표시: `compat{terrain_family: true|false, reason}`
- 보정값: `infrared_intrinsics`, `extrinsics`
  - `extrinsics.depth_to_color{R_row_major[9], t_m[3], R_sdk_col_major[9]}`
  - 정의: **p_color = R · p_depth + t**
  - SDK의 `rs2_extrinsics.rotation`은 열 우선이다. 열 우선으로 해석한 뒤 행 우선으로 직렬화하고, 원본 배열도 함께 저장한다
  - `depth_to_infrared`, `depth_to_accel`, `depth_to_gyro`도 같은 형식이다
- 좌표 규약: `frames_convention`
  - optical 좌표는 x 오른쪽·y 아래·z 앞, 단위는 m다
  - 왜곡 모델은 SDK가 보고한 값을 그대로 기록한다. `model`·`coeffs`가 0이면 정류된 pinhole이다
- 센서 옵션: `sensor_options{depth{…}, color{…}, motion{…}}` 스냅샷. IMU 단위는 accel m/s², gyro rad/s
- IMU: `imu{requested, available, first_sample_wall, reason}`. `available`은 **실제 샘플을 받았는지**로 판정한다
- 통계(종료 때): `stats`
  - 수집 측: `framesets_received`, `skipped_warmup`, `skipped_every`, `dropped_app_queue`
  - SDK 측: `sdk_frame_number_gaps{depth, infrared, color}`
  - 저장 측: `saved`, `write_errors`, `imu_samples{accel, gyro}`
  - 시간: `duration_s`, `monotonic_start`, `monotonic_end`

`frames.csv` 열:
- `save_idx`, `capture_idx`
- `host_mono_s`(수신 단조시각), `host_wall`
- 스트림마다: `depth_ts_ms`, `depth_ts_domain`, `depth_fn`, `ir_ts_ms`, `ir_ts_domain`, `ir_fn`, `color_ts_ms`, `color_ts_domain`, `color_fn`

`imu.csv` 열: `host_mono_s`, `kind`(accel|gyro), `ts_ms`, `ts_domain`, `fn`, `x`, `y`, `z`

### 1.4 수집 구조
- **한 pipeline에 콜백 하나**로 영상(depth·IR·color)과 IMU(accel·gyro)를 함께 받는다. 레포 Gateway와 같은 방식이고, 장치 API를 pipeline과 섞지 않는다
  - IMU 요청이 실패하면 영상만으로 다시 시작하고, 이유를 기록한다
- 콜백 안에서 하는 일(짧게):
  - frameset이면 각 스트림 버퍼를 **독립 연속 배열로 복사**하고, 스트림별 타임스탬프·도메인·프레임 번호를 붙여 `capture_idx`를 발급한다
  - warm-up 30개를 넘긴 뒤 `every` 간격에 맞으면 `put_nowait`로 저장 큐에 넣는다. 큐가 차면 버리고 `dropped_app_queue`를 센다
  - motion 프레임이면 IMU 버퍼(잠금 있는 리스트)에 붙인다
- 저장 큐 기본 크기는 60이다(640×480 깊이·IR + 1280×720 컬러 기준 약 210 MiB).
- 저장 스레드 4개가 불변 배열만 받아 PNG(압축 1)·JPEG 95로 쓴다
  - 성공하면 결과를 `(save_idx, row)` 형태로 완료 목록에 넣는다
  - **쓰기 실패는 즉시 오류 플래그를 세우고 기록을 멈추며, 종료 코드는 0이 아니다**
- `save_idx`는 큐에 넣을 때 연속으로 발급한다. `frames.csv`는 종료할 때 한 주체가 저장 성공 프레임만 `save_idx` 순으로 쓴다. 쓰다가 죽어도 남도록 `capture_log.csv`는 수집 측이 순서대로 바로 쓴다
- 종료 순서: 생산 중지(pipeline stop) → 큐 처리 완료 → 저장 스레드 종료 → IMU·통계 확정 → meta 쓰기
- `--frames N`은 **저장 성공 수** 기준이다
- 상태 줄은 0.5 s마다 갱신한다: 경과 시간, 저장 수와 실효 Hz, 큐 길이, 버림(큐·SDK 번호 틈), IMU 수, 깊이 유효 비율, 가운데 거리
- 이 정책(새 프레임 버림)은 오프라인 기록용이다. 실시간 처리는 "최신 프레임 우선"이라는 별도 정책을 쓴다

### 1.5 Gateway 단일 소유권 보호
- 이 도구는 **노트북에 L515를 직접 꽂은 개발 기록용**이다. 로봇에서는 Gateway 토픽을 rosbag으로 기록한다(→ 나중에 `bag_to_seq.py`로 같은 형식으로 변환)
- 시작할 때 다음 중 하나라도 맞으면 SDK를 열지 않고 종료 코드 2로 끝낸다:
  - `/run/powertrain/l515-gateway.lock`이 있음
  - `gateway_main` 프로세스가 돌고 있음
  - 젯슨(`/etc/nv_tegra_release` 있음)
- 젯슨에서 정비 목적으로 직접 써야 하면 `--maintenance`를 준다(Gateway와 감독 재시작을 사람이 먼저 멈춘 상태가 전제다). 이때는 잠금 파일을 생성·절단 없이(`O_RDWR`, `O_NOFOLLOW`) 열고 소유자·권한을 확인한다. 그다음 `flock(LOCK_EX|LOCK_NB)`을 얻어 **모든 SDK 센서를 닫을 때까지 유지**한다. 실패하면 종료한다
- 파일이 없다는 것만으로 노트북이라고 판단하지 않는다. 젯슨 판별을 따로 한다

### 1.6 `terrain_node.py`(ROS 노드 호환, 별도 커밋)
고칠 것은 네 가지다:
- 내부 파라미터를 `camera_info`에서 받아 초기화
- 깊이 변환은 1회만
- 토픽 기본값을 `/l515/depth/image_rect_raw`로
- UDP 포트 기본값을 :5003에서 바꿈

컬러가 없는 경우의 처리도 넣는다. 이 수정의 인수는 젯슨 격리 스모크(AGENTS.md §5)로 따로 받는다. L0 완료와 섞지 않는다.

### 1.7 점검 도구 `check_seq.py <폴더>`
- meta 필수 키·형식 버전을 확인한다
- 파일 쪽:
  - 스트림별 파일 수·번호 연속성, frames.csv와 파일 집합 일치 여부
  - 표본 파일의 dtype·크기가 meta와 같은지
  - 깊이 단위가 0.25 mm인지
- 시간 쪽:
  - 스트림별 타임스탬프 **역행·중복**
  - 프레임 번호 틈
  - 같은 frameset 안 depth–IR–color 시간차(같은 도메인일 때만 뺀다)
  - IMU 주기·역행
- 버림 통계를 종류별로 출력한다
- 표본 프레임의 깊이 유효 비율과 가운데 거리를 낸다
- 구조 오류가 있으면 0이 아닌 종료 코드로 끝낸다

### 1.8 검증(AGENTS.md §5: 실제 실행 + 실전 경로 + 음성 대조)
1. **단위 시험**(pytest, 장치 없이):
   - 가짜 소스 → `SeqWriter` → `check_seq` 통과
   - 인수받은 `terrain.load_detector`가 탐지기를 만들고, **`process()`가 합성 바닥 깊이에서 OK와 맞는 카메라 높이를 낸다**
   - 외부 파라미터 직렬화: 비항등 회전 합성 투영 대조(열 우선 → 행 우선)
2. **음성 대조**(알려진 결함 주입 → `check_seq` 실패 확인):
   - 깊이 파일 하나 삭제
   - dtype을 uint8로 바꿔 저장
   - 크기 불일치
   - 깊이 단위 오기
   - 타임스탬프 역행
   - 쓰기 실패(쓰기 금지 디렉터리) 시 종료 코드
3. **실기**:
   - 노트북 L515로 10 s 기록(IMU 포함) → `check_seq`
   - 인수받은 `terrain.py <폴더>`·`ground.py <폴더> 5`가 돌고, 책상 높이·기울기가 줄자·수평계와 맞는지 본다
   - 실제 협상 프로필을 meta에서 확인한다

### 1.9 기록 절차(기록할 장면)
| 장면 | 방법 | 같이 적을 것 |
|---|---|---|
| S1 벽 잡음 | 평평한 벽 정면 0.5/1/2/3/4 m(기본 min_distance 0.49 m이므로 0.5 m가 하한), 1·2 m에서 45°. 각 5 s 정지 | 줄자 거리, 벽 재질 |
| S2 바닥 + 상자 | 수평 바닥, 로버 장착 높이(약 0.45 m, 아래로 약 20°)에 고정. 치수를 아는 상자 2~3개를 1~2 m에. 임계 근처 높이(3·7 cm 단)·얇은 물체·어두운 면 포함 | 카메라 높이·기울기, 상자 치수·위치 |
| S3 걸으며 한 바퀴 | S2 높이·각도로 들고 천천히 한 바퀴. **시작·끝은 같은 받침 위 같은 자세** | 경로, 받침 위치 |
| S4 단·도랑 | 실제 문턱·계단 첫 단·연석. 실제 도랑(배수로 등)은 있으면 | 높이·폭·깊이 |

## 2. 3D 지도 L1 — `lidar_dev/map_seq.py`(오프라인)

1. **입력·전처리**: 원시 uint16 깊이와 같은 격자의 IR을 쓴다. Open3D `RGBDImage.create_from_color_and_depth(ir, depth, depth_scale=1/depth_scale_m(≈4000), depth_trunc=4.0, convert_rgb_to_intensity=True)`로 넣는다. 깊이는 0.25–4.0 m만 쓰고, 3×3 최대/최소 비 1.12 경계 필터를 건다(Isaac 시뮬 현실화 모델의 경계 필터와 같은 방식). 컬러 정렬판 비교는 후처리 정렬(meta 외부 파라미터, 컬러 K)로 한다
2. **자세 추정**(source = 현재 프레임, target = 현재 키프레임):
   - 초기값: 직전 프레임 상대 자세(등속 가정)
   - `compute_rgbd_odometry`(Hybrid). **성공 플래그 false면 실패**로 본다
   - 점–평면 ICP 보정: 법선 추정 반경은 복셀의 3배, 해상도는 복셀 4·2·1 cm, 대응 거리는 각 해상도에서 복셀의 2배다
   - 수용 조건: ICP fitness ≥ 0.6, inlier RMSE ≤ 1.5 cm, 프레임 간 이동 ≤ 15 cm·회전 ≤ 10°, 시간 틈 ≤ 0.5 s. 바닥·벽만 보이는 장면이라 정보 행렬의 최소 고유값도 본다(퇴화 방향 경고)
   - 하나라도 어기면 `TRACKING_LOST`로 처리한다. 그 프레임은 TSDF에 넣지 않는다. 다음 프레임은 마지막 키프레임에 다시 정합하고, 1 s 넘게 잃으면 지도를 나눈다
   - 합성: **T_world_cur = T_world_key · T_key_cur**. TSDF `integrate`에는 extrinsic으로 **inv(T_world_cur)**를 넣는다
   - 새 키프레임은 5 cm 또는 5° 넘게 움직였을 때 만든다
3. **중력 정렬**:
   - IMU가 있으면: 정지 구간(자이로 크기 작음)의 가속도 평균으로 중력을 정하고, depth←accel 외부 파라미터로 카메라 좌표에 옮겨 roll·pitch를 정한다. 움직이는 구간의 가속도는 쓰지 않는다
   - IMU가 없으면: **수평이 확인된 바닥**에서 시작한 경우에만 첫 바닥 평면을 기준으로 쓰고, 결과에 "초기 평면 기준 지도"라고 표시한다. 평면은 지지 면적·공간 분포를 검사한다
   - 지도 좌표: z 위, 원점은 시작 카메라 바로 아래 바닥, x는 시작 시 카메라 앞 방향의 수평 성분, 단위 m
4. **통합**: `ScalableTSDFVolume`(복셀 1.5 cm, 절단 4.5 cm, color_type Gray32)에 처음 프레임들과 키프레임을 넣는다. 키프레임 사이 최대 0.5 s마다 한 장은 넣는다. 3·7 cm 단과 얇은 물체가 보존되는지 평가한다
5. **루프 보정(선택)**: 시간적으로 떨어진 키프레임 중 시야가 겹치고 정합 품질이 수용 조건을 넘는 쌍만 간선으로 건다 → `global_optimization` → **최적화 뒤 원본 키프레임을 다시 통합**한다
6. **출력**: 점구름·메시, 프레임별 자세·추적 상태 CSV
7. **평가**:
   - S3: 같은 받침의 시작·끝 자세 차이를 루프 보정 전·후로 따로 보고한다
   - S2·S4: 지지면 기준으로 정한 위치에서 상자·단 높이를 3회 이상 재서 평균·표준편차를 실측과 비교한다
   - 처리 시간(프레임당)

## 3. 장애물 인식 L2 — `lidar_dev/obstacles_map.py`

> **구현 메모(10-18, v3)**: 아래는 설계 목표다. 구현된 v3는 두 층(`level_local` 국소 위험, `level` 출발 지지면에서의 경로 허가 — 칸 단위 병목)이고, 머리 위 틈은 부분 지원, FREE는 미구현이다. 실제 규칙과 검증은 `docs/plans/2026-10-18-l515-seq-l1-plan-and-log.md`의 "교차검토(4차)"·"교차검토(5차)" 절을 따른다.

1. **관측 상태와 지형 분류를 나눈다**
   - 관측 상태: `FREE`·`OCCUPIED`·`UNKNOWN`. 카메라 자세·시야·광선과 실제 깊이 관측으로 칸을 갱신한다
   - 관측되지 않은 칸은 `UNKNOWN`이고, 통행 여부도 `unknown`이다
2. **높이는 넷으로 따로 계산한다**:
   - 절대 표고(지도 z)
   - 국소 지지면 대비 돌출 높이(레포 `grid.py`처럼 주변 지지면 기준)
   - 인접 지지면 단차
   - 국소 경사
3. **칸 통계**:
   - 지지면 통계와 돌출면 통계를 나눈다
   - 강건 통계(분위수)를 쓴다
   - 독립 관측 수와 최소 지지량(점 수·관측 프레임 수)을 둔다
4. **지형 분류**: 기준값은 시뮬 담당(도현)의 기준값 JSON(`obstacle_criteria_v0.json`, 레포 반영 시 `lidar_dev/config/`에 둔다)(v0.1, 실험 프로필 `l2-exp-v1`)가 **단일 정본**이다. 문서·코드는 값을 옮겨 적지 않고 이 파일과 버전을 참조한다.
   - v0.1 요약(정책값, 실기 한계 아님): 턱 5/7 cm, 내려가기 15/30 cm, 도랑 폭 12/18 cm, 경사 15/25°, 거칠기(평면 잔차) 3/5 cm, 통로 1.30/1.05 m, 머리 위 1.00/0.90 m. 구간은 반개구간이고, 불가 > 주의 > 통과 순이며, 미확인은 경로 허가로 쓰지 않는다
   - (2판 초안의 "경사 30° 초과 불가"는 v0.1의 25°로 바뀌었다)
   - 도랑은 깊이·폭·접근 방향을 별도 속성으로 둔다. **시뮬 "도랑 18/19 cm"는 깊이 0.5 m 틈의 폭 시험이다**(실제 형상 시험은 18/20 cm). 깊이 기준이 아니다. 5 cm 칸으로는 18과 19 cm를 가를 수 없다는 한계도 적는다
   - **지형 형상과 차량 통행 판정을 나눈다.** 통행 판정에는 폭·바퀴 경로·차체 외곽·접근각·불확실성·실차 검증 범위를 쓴다. 10-23에는 형상 분류까지만 하고, 통행 판정은 표시용 초안으로 둔다
   - 인수 코드(바닥 3 cm / 장애물 5 cm), 레포 코어(지지면 연결 12 cm / 낙하 18 cm / 장애물 15 cm), 새 L2의 기준 차이를 표로 남긴다
5. **연결 영역**:
   - 8-연결로 묶되 같은 분류 안에서 높이 차가 5 cm를 넘으면 나눈다
   - 분류 우선순위: 벽 > 장애물 > 낙하 후보 > 경사 > 낮은 턱 > 지지면
   - ID는 **지도 버전 안 ID**다(추적 ID 아님). 10-23 인수는 정적 장면만이다
6. **출력**: 새 메시지 타입 `terrain_map`(`schema_version`, `map_version`)
   - 필드: 좌표 프레임, 촬영 시각 범위, 로버(카메라) 자세, 거리 정의, 품질 상태, 만료 시간
   - 장애물별: `poly_xy_m`(지도 좌표), 높이, 분류, 관측 품질
   - 인수받은 `packet.py`의 `poly`는 1280×720 컬러 영상 픽셀이고 `dist_m`은 전방거리 분위수라, 의미가 다른 필드를 섞지 않는다. 영상 투영을 다시 쓸 때는 `poly_px`로 따로 두고, 공칭 평행이동 대신 meta의 공장 외부 파라미터를 쓴다
   - 관제탑 전송은 새 포트 :5009(수신기·순서 번호·데이터그램 크기 계약과 함께)를 제안한다. 10-23 범위 밖이다
