# Remote driving CAN recovery and automatic resume

User authorization: resume robot motion when CAN communication recovers; implement, test and deploy while the user is not driving (2026-09-10). Operator E-stop, disarm, lost/stale manual input and other safety faults must continue to stop and cancel pending resume. Autonomy is outside this change.

## Contract

Firmware patch3 keeps the existing immediate PWM stop and zeroed inputs during CAN hardware recovery. It exposes an explicit recovery origin on the existing heartbeat: byte4 axis state stays unchanged; byte5 marker0xA3; byte6 flags bit0 recovery latch, bit1 recovery in progress, bit2 automatic-resume eligibility; byte7 uint8 recovery generation. Old firmware is never inferred eligible from axis_error0x4000 alone. The standard five-byte prefix remains unchanged.

Eligibility is granted only when an automatic HAL recovery interrupts healthy CLOSED_LOOP. Repeated recovery attempts preserve an already-granted eligibility, but never create it from an IDLE, explicit E-stop or manual CAN reinitialization. Explicit CAN E-stop, manual USB CAN reinitialization, clear_errors and MCU restart revoke eligibility. Firmware never re-arms itself or replays cached setpoints. Existing Config_t/NVM layout and watchdog semantics remain unchanged.

ChassisManager owns recovery across all six CAN drive axes. An already armed remote manual session may pause for a verified patch3 CAN recovery (or observed CAN feedback loss, pending later fresh stopped evidence). It stops all outputs, discards cached motion and uses a dedicated internal hold; unrelated faults still latch normal E-stop. Recovery is bounded to5s and requires at least200ms of stable fresh six-axis heartbeat+encoder feedback, stopped wheels(<0.1wheel rev/s), healthy steering, no other safety holds, fresh manual input and matching configured node identities. A flagged error must be exactly0x4000, IDLE, not in recovery, eligible; plain error0 axes are allowed as unaffected peers. Unknown/mixed errors, unmarked0x4000 and manual firmware recovery cannot auto-resume.

The episode records every drive node observed missing/stale or eligible, starting with the triggering sample. Every such node must supply its own eligible recovery origin; another axis's eligibility cannot excuse a rebooted/error0 peer. Only continuously fresh unaffected axes may use the error0 peer path. After re-arm, a new command remains held until one tick has validated every drive and steering sample before dispatching any nonzero command. A stale steering axis in WAIT_INPUT cannot release the hold or permit a partial five-wheel command.

The host requests the atomic guarded RESUME described below for affected axes, zero/ordinary arm without clear for continuously fresh healthy peers, and confirms fresh error0/state8 feedback through the existing bounded arm path. It then waits for an actual manual command receipt newer than re-arm completion before releasing the hold. ROS must carry the source receipt time, never rejuvenate it on50Hz selection ticks. Disarm/E-stop/authority loss/packet timeout/component changes cancel recovery permanently; explicit manual start is needed afterward. No MCU reset, saved start flags or firmware telemetry alone may resume motion.

The source receipt is the Jetson gateway's monotonic TCP-frame receive time, bound to the speed/steering payload in `ManualDriveCommand.source_received_s`. DDS receive time remains a separate executor-backlog check. A gateway's50Hz republication cannot update the TCP receipt or release recovery; a separately published gateway state only cancels on disconnect/staleness and never grants a command fresh provenance. Legacy Twist manual driving remains supported, but its unstamped payload cannot request automatic CAN resume.

`ManualDriveCommand.connection_session_id` binds the server-generated accept UUID to those same values. The UUID also appears in gateway state. A connection change cancels the pending episode even when disconnect/reconnect/neutral all occur before one gateway publication; client-supplied session IDs cannot substitute for this server epoch. Deadman release is an ordinary zero command and is separate from explicit disarm; a fresh zero may resume into zero output without replaying an older nonzero command.

Normal chassis healthy/qualified wheel-stop gates remain strict. Recovery state/count/reason are observable without claiming the chassis healthy during recovery. Host old-firmware support remains available for normal manual operation, but automatic recovery requires unambiguous evidence.

Automatic resume is one firmware-guarded operation, not a manual clear followed by an ordinary arm. CAN command0x07 has DLC8 with `<IBBBB` payload `(8, 0xA3, expected_generation, 0, 0)`. In one critical section, the board requires eligible+latch, no recovery in progress, IDLE, no pending non-IDLE state, exact0x4000, matching generation, all underlying motor/encoder/controller/sensorless errors0, and no new HAL/reinit pending condition. Only then does it clear, zero the inputs and request state8 atomically. A rejection changes no error and cannot authorize arm; the host never follows a rejected guarded command with an ordinary arm. Command0x18 remains manual zero8/legacy empty clear only. Automatic re-arm sends no clear at all to unaffected error0 peers. Patch2 markerA2 is not eligible because it lacks the guarded RESUME operation. An external manual clear before guarded RESUME cancels eligibility and cannot turn a rejected operation into an automatic arm.

## Acceptance

- RED then GREEN: real firmware-source recovery origin/heartbeat scenarios; Python frame decoding, coordinated stop/rearm/fresh-receipt path and cancellation cases.
- All related host/ROS regressions; reproducible Cortex-M4 build with NVM layout unchanged.
- Installed ROS/vcan loop proves fault→pause→guarded RESUME→new input→resume and negative E-stop/disconnect/stale-command cases.
- Physical board update uses exact serial, two-read full-flash backup and guarded application-only DFU. Readback preserves NVM/config/calibration.
- Physical commissioning uses zero drive commands to verify fault/recovery with no intended movement. Actual nonzero driving and repeated ground acceptance remain separately reported.
- Hardware scope is the USB-identified boards13/14 and15/16. Node11/12 firmware remains unverified and unpatched; a loss on those axes cannot be inferred eligible. Team Jetson checkout is preserved. No commit/push without the applicable user authorization.
